Wiring the Strategy Builder

Five primitives, three commands (one per deliverable), and the gates where a person still decides. What exists today, and what it takes to stand this up on a project that has nothing.

The five primitives

A skill is knowledge, a command is a procedure, a subagent is a separate context, a hook is a mechanism the host runs whether anyone remembers or not, and a plugin is a box. Reaching for the wrong one is the commonest way this gets built badly.

Skill

Knowledge the model loads when the work matches. It runs nothing and sequences nothing, which is why the shared discipline lives here instead of being copied into each command.

function-to-strategy-derivation · use-case-portfolio-derivation · derivation-orchestration · analytical-document-build · html-style · arc-watcher · storyline-review

Command

A procedure you trigger by name. It has a fixed entry, a fixed sequence, and it holds the gates. There are three, one per deliverable, each with one audience, and a fourth that reads the chain they produced backwards.

/build-strategy · /build-portfolio · /build-recommendation · /review-storyline

Subagent

A separate head with its own context and its own tool budget. Its work costs you the reading of its findings and nothing else.

strategy-critic · stakeholder-proxy · storyline-reviewer

Hook

A script the host runs at a lifecycle event, without being asked. The other four are instruction, and an instruction is dropped under load with no signal; a hook is the one primitive that fires anyway. It cannot decide anything, and only one of the three has output the agent reads. Where each fires is on the run.

precompact-closeout.sh (PreCompact) · sessionstart-resume.sh (SessionStart) · render-progress.sh (Stop)

Plugin

Ships commands, skills, subagents and hooks as one versioned unit you can install. The repo root is the plugin root, so there is no second copy of anything in this repo.

How they wire together, where the run stops, and what fires on its own

Every stage names the artefact it derives from, so a later stage can be checked against its own input. The gates are decisions the method cannot make, and the run stops at each one until a person answers. Below the diagram: the mechanisms that run without being remembered, and the inventory of what exists.

The run What fires on its own What exists

Why the gates are batched. Rulings arriving one at a time are what consume a person's day, whatever the analysis costs. A gate presents every open decision at that point, each with a recommendation and what it costs to go the other way, and takes them in a single pass.

Where the storyline review sits. Not on the diagram, because it is not a stage of the run but a reading of it. Once two of the storyline stages exist, /review-storyline reads the chain backwards, drafts a verdict on every handoff between consecutive stages, and puts each one to you as a question with options. Its two gates are yours and nothing in it is a deliverable.

Where plan mode is on. The dashed marker under the left edge of each command, bracketing only its entry and its first gate tick. The command's first action is to ask for the host's read-only mode, and the mode stays on through the guards and the entry gate: Gate 0 for the strategy, P1 for the portfolio, R1 for the recommendation. The entry report is the plan; approving it is what makes the first write legal, and that write is the ruling register. On a resumed run the resume report is the plan instead, so you see where the command thinks it is before it touches a file. It ends before stage 1 and is never re-entered at a mid-arc gate, where a read-only mode would block the reviewer's file and the stage commit.

What fires on its own, and where

Most of the method is instruction, and an instruction is dropped under load with no signal. The things in this table are the ones that are not: a host mode that blocks writing, and three hooks the host runs whether anyone remembers them or not. Each row says where it applies, who sees it, and what it cannot do.

Plan mode
the host's read-only mode		 Steps 0 to 0b of /build-strategy: the intake read, the guards, and Gate 0. The resume report on any later run. The entry of the other two commands in the same shape. Not Gates 1 to 8, which rule on artefacts already written and reviewed, and where a read-only mode would block the reviewer's file and the commit. You. Close-out hook
hooks/precompact-closeout.sh		 Before a context compaction, manual or automatic, while the context still exists. Checks for uncommitted work and for a handoff.md that is behind the last commit. You, as a warning. Its output does not reach the agent, and it cannot stop the compaction. It is a prompt to say “commit and update the handoff first” while the reasoning is still there to write from. Fire on /clear. hooks/sessionstart-resume.sh		 After a clear, a compaction or a resumed session, in any folder that holds a handoff.md. The agent. This hook's output is read into the fresh context, so it re-injects the resume document, bounded, with the instruction to derive the resume point from the files rather than from the document. Hook guard
step 0a		 Before stage 1, with the other guards. Looks for a registered close-out hook in user settings, project settings or the installed plugin. You, at the first gate report. A miss is a warning rather than a stop, because the run can finish without it; what it cannot do is claim the context boundary was guarded. Tell you the hook will fire, or how many times. Progress page
arc-watcher · RUN-PROGRESS.html		 At the end of every agent turn, in any folder holding an intake.md, through a Stop hook. Also one line of position after a clear, compaction or resume, through the resume hook. On demand from the skill's script. You, in a browser. The arc the run is in and where it stands; an approximate percentage complete, overall and per arc; a strip of every stage and gate; for every row the reason for its state and what it waits on; which gates were ruled (a ruling row is on file) and which merely passed (the run went on); which reviewer passes are on file; a list of things to look at, each of which belongs in the next gate report; and the close-out state. The agent sees only the one-line summary. Know anything the files do not say. Ruled is a row that matched a pattern, not a ruling read; passed is a later artefact, not a decision. Presence is not quality. A stage missing while later ones exist is reported as not on file: the page cannot tell a skipped stage from one added to the method after the arc ran.

Why the hooks ship inside the plugin. The first one existed for four days in one machine's user settings while the command printed a one-line copy of it that had already drifted. It was present where it was least needed and absent everywhere the plugin travelled, and the only record of it was the author's memory. A mechanism the method depends on ships in the same package as the method, or the method says plainly that it does not.

The absence produced no signal, because a hook that did not fire looks exactly like a compaction that did not happen.

A hook registered twice fires twice, and two of the three are not harmless doubled. The plugin registers the hooks; a development install registers the same files a second way; the host runs both. The day after they shipped, the resume document arrived in the fresh context twice and the page rendered twice a turn. The doubling had only been thought about for the close-out warning, the one hook whose output the agent never reads.

Each script is now idempotent per session and event: it reads the session id the host hands it, and a second fire within seconds exits before doing anything. Both registrations stay. Corrected 2026-09-12.

What plan mode is for here, and what it is not. The method already had a rule that nothing is written before the two entry rulings are made. Plan mode turns that from a sentence the agent reads into a property of the host it runs on. It is not a review step and it is not a second gate: the gates are unchanged, and the person rules the same two things at the same point. What changed is that the host now enforces the ordering.

The plan file lives outside the repository and no resume reads it. So the approved plan is copied into the ruling register as the first write, before the instruction file and before the frame. A ruling that exists only in the plan is a ruling from memory.

Standing it up on a new project

Seven steps, about twenty minutes. Most of it you do once per computer, not once per project.

Steps 1 and 2 are one-off. Everything from step 3 is what you do each time you start a new piece of work.

  1. Install it, once per computer

    Type two lines into Claude Code. That gets you the three commands, the skills, the two reviewers and the three hooks. You do not do this again on this machine.

    /plugin marketplace add Gerhardcvdm/S2P_Strategy_Builder /plugin install s2p-strategy@s2p-strategy-builder

  2. Restart Claude Code

    The reviewers are only picked up when a session starts. If you skip this, nothing appears to go wrong; the work simply never gets reviewed, and the result still looks finished.

  3. Make a folder for the work

    One folder per engagement. Put a short CLAUDE.md in it saying what the work is and, more importantly, what may not be put in the folder. The commands create the rest as they go.

    strategy/ portfolio/ client/ demo/ deliverables/

    Once the first command has run, the folder also holds RUN-PROGRESS.html. Open it in a browser whenever you want to know where the run is. It is rebuilt from the files at the end of every turn, so it is never stale and never worth editing.

  4. Fill in the intake

    Eight questions, in a file called intake.md. The form ships as a file, templates/intake.md, so you can read it, fill it in and arrive with it done. You no longer have to run the command and let it fail to find out what it wants.

    All eight are facts or settings you can state: what material may touch the folder, what the client may lawfully feed a model, whether this is commissioned or targeted work, and who and what it is about.

    The two hard ones are no longer on the form. The sentence you are claiming, and who the work is for, are decisions between options rather than facts. The command reads everything else first, then puts them to you at Gate 0 with three or four candidates each and what it costs to pick wrong. You still rule them, against named alternatives instead of a blank box.

    On a full run these two came back unusable three times in a row, in the same shape each time, while the six factual fields were right by the second pass. A field that fails three times against a well-written definition is a field posed as the wrong kind of question, which is what Gate 0 fixes.

    Nothing starts until the form is filled in. The command also checks that you replaced the template rather than only creating it, because otherwise the blank form would count as a completed one.

  5. Run the first command

    It works on its own until it needs a decision, then stops and asks you. If you run out of session, run it again: it reads the files already on disk and picks up where it left off.

    The first thing it does is ask to enter plan mode. Say yes. In plan mode it can read and check but cannot write, and it stays there through the intake, the guards and Gate 0. The Gate 0 report arrives as a plan for you to approve; approving it is what lets the first file be written. On a later run the same happens with the resume report, so you see where it thinks it is before it touches anything.

    /s2p-strategy:build-strategy

  6. Answer it when it asks

    This is the part that does not automate, and the part everything else is built around. It asks in batches, every open decision at once, each with a recommendation and what the other answer would cost you, so you rule in one sitting instead of being interrupted all day.

  7. Run the other two

    The portfolio carries on from the strategy and reuses its numbering. The recommendation only writes up what the portfolio already established and works out nothing new.

    /s2p-strategy:build-portfolio /s2p-strategy:build-recommendation

  8. Read it backwards before it goes into a room

    Once two stages exist, and again when more do. It drafts a verdict on every handoff between stages and asks you about each one, with the two sentences it rests on in the question. Nothing it writes is a deliverable.

    /s2p-strategy:review-storyline

The one thing the commands cannot check for you. Each command makes sure its reviewers are installed before it starts. Installed is not the same as loaded: a reviewer added during a session sits on disk unnoticed and still passes the check. That is why step 2 is a step and not a footnote.

The principle underneath it applies well beyond this: a check that cannot find what it is looking for does not fail. It passes.

What each stage produces, and what each gate asks

The gates are the product. They are where the judgement stays yours, and a run is planned around them rather than around the stages. Two are irreversible; the rest can be revisited at a cost.

What it costs, measured rather than guessed

One complete arc, with production, review and rebuild separated at the time rather than reconstructed afterwards. The agent phases are measured. The human phases are not, and saying so is the point.

PhaseObservedWhat it means for planning
A stage artefact10–20 minThe part that looks like the work, and the smallest part of it

Why two rows say “not separable” instead of a number. An earlier version of this page published a measured gate wait of 119 minutes against 13 to apply the rulings and 5 to produce the stage it blocked, a ratio of 6.6, as the reason gates are batched. The timestamps were real. The figure was still wrong for the claim, because a large part of that span was waiting for model tokens to refresh, not deliberating. Corrected 2026-09-07, on the operator's own correction.

An elapsed span across a human measures the environment, not the person. It contains deliberation, absence and platform limits, and a timestamp cannot tell them apart, so it misleads most exactly when it is largest. The only instrument that can separate them is one line from the person who was waiting.

The batching rule survives without it: serialising n rulings costs the human n returns to a document they had put down, whatever each ruling takes.

Two levers govern what a reviewer pass costs, and only one of them has moved. The first is what it reads. Unbudgeted, each pass read more of the chain than the one before it, so a budget shipped on 2026-09-12: every check kept, the reading narrowed to the sections a check needs, and each pass now reports what it opened with line counts. The second is the model it runs on, and that one is deliberately unset. Both subagents inherit the session's model, ruled 2026-09-14.

The argument for pinning a model would be reproducibility, not saving. The only agent run often enough for a cheaper model to save anything is the reviewer, and its findings are the output, so the place where a downgrade would pay is the place a capability drop costs most. An inherited model is still a variable the record does not carry, so a finding count compared across sessions is compared across an unknown.

Move one lever at a time. A pass that returns fewer findings after both changed says nothing about either.

Reviewer findings do not fall as the chain matures. Across twelve consecutive passes on one run: 9, 18, 14, 12, 12, 10, 18, 13, 16, 12, 14, 15, a mean of 13.6 with no trend. Each stage introduces new claims and new quotations from upstream registers, and maturity in the earlier artefacts does not protect the next one.

Read a flat rate as evidence that per-stage review is still necessary at the end of a chain. It is not the reviewer padding, and a falling rate is not the goal, because a rate that falls may only mean the reviewer was narrowed.

What a specification is worth. Rebuild-to-production ratios across three consecutive stages ran 1.3, 4.8, 0.9. The stage that broke the pattern was the largest artefact in the run and the only one built against a written contract.

It did not reduce the defect count. The reviewer still raised fifteen findings against it, in line with every other pass. It changed what each defect cost. The earlier stages were deciding what the artefact should contain while writing it, so any finding touching scope forced a re-derivation; the specified stage had already settled scope, so findings landed as edits. Same defect rate, roughly a fifth of the rework.

This holds only if the specification is itself reviewed first. That one was, and it was wrong in fourteen places, four of them omissions that would have been built faithfully.

Two ways in, and which is which

The repo root is the plugin root, so nothing is copied into a package directory inside this repo. That is the whole reason it took this shape.

That is a fact about the repo, not about the machine, and the machine has three copies. Corrected 2026-09-07; this page used to say there was no second version to keep in step.

So an edit made here is already live for the bare command and invisible to the namespaced one. Both failures are silent: the junction gives no signal that something went live unreviewed, and the plugin gives no signal that it is behind. It keeps working, on the old text, under the same command name.

Before relying on “nothing goes live until it is installed”, resolve where the loaded copy comes from.

Distribution: the plugin

Two commands and everything arrives together, versioned, on any platform. No clone, no script, no known path.

/plugin marketplace add Gerhardcvdm/S2P_Strategy_Builder /plugin install s2p-strategy@s2p-strategy-builder

Updates arrive only when the manifest's version is bumped, so a reader is never surprised by a method that changed under them.

Development: junctions

Directory links from the tool's install folders into this repo. An edit here is live everywhere immediately, with no reinstall and no version to bump.

pwsh adapters/claude/install.ps1 -Apply

Windows-specific, and it needs the repo cloned first. That is acceptable for the machine the method is written on and unacceptable for anyone else's.

Both can be active at once, and they answer to different names. The junctioned copy is /build-strategy; the plugin copy is /s2p-strategy:build-strategy. Plugin commands are always namespaced, which is why the plugin ID is the short s2p-strategy: the prefix gets typed in front of client work.

Convenient while developing, confusing afterwards. If both are installed, know which one you are running before concluding that an edit did or did not take.

The hooks follow the same split. The plugin registers them from its own hooks/hooks.json; the junction install has no plugin root, so install.ps1 writes an entry into your user settings that points at the repo's copy of the same three files. If both installs are active each hook is registered twice and would fire twice. The scripts are idempotent per session, so the second fire exits: one warning, one resume document, one page render.
